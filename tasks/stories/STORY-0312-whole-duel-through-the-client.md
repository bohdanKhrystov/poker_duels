## Goal

One test drives the client from `Hello` to `DuelFinished` over a scripted sequence of real server
frames, asserts what the player sees at each step, and proves that the opponent's cards never
reached the screen before the server revealed them.

## Why

Every earlier story tests a part. A leak in this client will not come from a part — it will come
from composition: a store that keeps a frame a screen then renders, a log that shows an event the
table redacted, a reconnect that repaints stale state. `EPIC-02` closed on exactly this kind of test
for the socket; this is its mirror on the other side of the wire.

## Design notes

- **The frames are real.** They are produced by the server's own encoder — captured from an existing
  server test run, or generated by one — never hand-typed. A hand-typed fixture encodes a client
  author's belief about the wire, and a fixture that can disagree with the protocol is worse than no
  fixture. Typed as `ServerMessage` from `protocol.gen.ts`, so a protocol change breaks this test at
  compile time.
- How the fixture is obtained and committed is a ticket-level choice constrained by `DEC-022`'s
  toolchain; whichever it is, the test must not need a JVM, a server, or a database to run.
- The duel scripted is a complete one: several hands, at least one showdown with a reveal, at least
  one hand won without a showdown, and a `DuelFinished` with a winner.
- **The secrecy assertion is over the rendered output**, not over the store: at every step before
  the revealing snapshot, no rank/suit pair belonging to the opponent's seat appears in the DOM. A
  store-level assertion would miss the one path that matters — something rendering a frame the store
  passed through.
- The test drives the fake socket the earlier stories established. Whether a real two-browser run
  exists at all is `DEC-024`, and its answer does not change this story.

## How the fixture is obtained

`DEC-022`'s toolchain leaves this a ticket-level choice, and the split takes `ADR-0020`'s existing
answer for `protocol.gen.ts` rather than inventing a second mechanism: one Gradle task writes
`web-client/src/e2e/scripted-duel.gen.json` from the server's own `ProtocolCodec`, a second
regenerates into `build/` and fails `:poker-server:check` on any byte of drift. So the frames are
real *and* cannot rot, and the client's replay needs no JVM, no server and no database — only the
committed file.

The script holds **both** seats' sessions, not one. That is what lets every client-side claim be made
twice from two genuinely different inputs: two hole-card sets, two verdicts, two `Act` sequences —
the discipline that stops an assertion passing because it happened to be true of a fixture default.

## Acceptance criteria

- [ ] One named test plays the scripted duel from handshake to `DuelFinished` and asserts the result
      screen's winner, hand count and final stacks.
- [ ] Across that run, no opponent hole card appears in the rendered output before the snapshot that
      reveals it — asserted at every step, not only at the end.
- [ ] The client sends exactly one `Act` per `YourTurn`, each echoing that turn's `handNumber` and
      `actionSequence`.
- [ ] A hand won without a showdown ends with no opponent card ever rendered.
- [ ] The test runs in the client's ordinary test command, with no server, database or JVM.

## Out of scope

- A browser end-to-end test against a running server — `DEC-024`, still open and still the
  architect's. When this story was written it reserved `STORY-0313` for that answer; `ADR-0045` has
  since taken that number for the presence story, so if `DEC-024` says yes it becomes `STORY-0314`.
  Corrected at the split rather than left as a dangling reference.
- Performance, bundle size and rendering budgets — nobody has set one.
- Visual regression or screenshot testing — the design review is visual and human (`ADR-0024`).
- Rematch in the scripted duel — `STORY-0309` is blocked on `EPIC-02`'s `STORY-0213` (`ADR-0044`),
  and this test does not wait on it. `OfferRematch` and `RematchOffered` exist in no Kotlin file and
  no generated type, so a script the server's own encoder produced cannot contain one; no ticket here
  depends on a rematch frame.
- Presence in the scripted duel — `OpponentPresence`, `SeatPresence` and `ActedForAbsentSeat` are
  `EPIC-02`'s `STORY-0214` and this epic's `STORY-0313` (`ADR-0045`), and are on the wire nowhere
  yet. Same reason, same consequence: no ticket here depends on a presence frame, and this story does
  not wait on either. Added explicitly at the split rather than left implied, because the phrase
  *"a whole duel, frame by frame"* invites a reader to assume every frame the wire will one day carry.
- Reconnection inside the scripted duel. The driver uses `openConnection`, not
  `openReconnectingConnection`: `STORY-0310` proved the resume, and a retry loop would put a timer in
  a file that has no business owning one.
