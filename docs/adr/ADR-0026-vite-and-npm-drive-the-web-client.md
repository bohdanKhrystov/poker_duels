# ADR-0026 — Vite and npm drive the web client, and its checks are their own CI job

- **Status:** Accepted
- **Date:** 2026-08-14
- **Resolves:** `DEC-022`
- **Unblocks:** `STORY-0301` (the `EPIC-03` scaffold), and through it every story in the epic

## Context

`ADR-0003` fixed React, TypeScript and Tailwind and stopped there. `STORY-0301` must now scaffold
the module every other `EPIC-03` story stands on, which means choosing the build tool, package
manager, Node version, test runner, lint/format tooling, the dev-time route to the Ktor server,
and the way client checks enter CI. Four forces shape those choices:

1. **`ADR-0003`'s own criterion.** The stack must be boring and abundant in training data —
   the client is the layer where generated code is supposed to need the least supervision, so the
   toolchain must be the one the models know best, not the one with the best benchmark.
2. **`ADR-0020`'s boundary.** The server build needs no Node; the web build needs no JVM. And
   `web-client/src/protocol/protocol.gen.ts` is generated by the Kotlin emitter, committed, and
   **byte-compared** by `verifyProtocolTypes` on every `./gradlew check`. Any client tool that
   rewrites that file puts the formatter and the emitter in a permanent fight: `check` goes red,
   regenerating appeases Gradle, the next format breaks it again, forever. This is the sharpest
   constraint in the decision.
3. **Two Node versions, no owner.** CI pins Node 20 (`TASK-020309`) for a single ad-hoc
   `npx tsc` step over the generated file; the workstation runs Node 26. Node 20 passed
   end-of-life in April 2026, so the pin is not merely inconsistent — it is unpatched.
4. **Development runs against the real server.** The Ktor server owns `/ws` and `/api` on
   port 8080 and is authoritative (`ADR-0002`); the client must reach it in development without
   CORS carve-outs on the server or per-environment base URLs in the client.

## Decision

**`web-client` is a Vite + npm project pinned to Node 24 by `web-client/.nvmrc`, tested with
Vitest, linted and formatted by ESLint and Prettier — both of which ignore
`src/protocol/protocol.gen.ts` by path — and checked by its own parallel CI job; the Gradle build
stays JVM-only.**

Concretely:

- **Build tool and dev server: Vite** (current major), with `@vitejs/plugin-react` and Tailwind
  via the first-party `@tailwindcss/vite` plugin. `vite build` emits static assets; there is no
  SSR and no client-side server runtime.
- **Package manager: npm**, already present as v11; `web-client/package-lock.json` is committed
  and CI installs with `npm ci`. No pnpm, no yarn.
- **Node: 24, the newest active LTS, pinned in exactly one place** — `web-client/.nvmrc` — which
  CI reads via `actions/setup-node`'s `node-version-file`. `package.json` declares
  `"engines": { "node": ">=24" }` so a too-old local Node is at least warned about. **CI
  governs:** green
  means green on the pinned version. The workstation's Node 26 is an acceptable mismatch because
  Node is a build tool here, not a runtime — the artefact is static files — and any behavioural
  difference surfaces in the CI job before merge. The EOL Node 20 pin is replaced, not kept.
- **Test runner: Vitest**, environment `jsdom`, with `@testing-library/react` for component
  tests. It shares Vite's transform pipeline, so tests exercise the same code the dev server
  runs, and its Jest-compatible API keeps the training-data advantage.
- **Lint and format: ESLint 9 (flat config: `typescript-eslint`, `eslint-plugin-react-hooks`,
  `eslint-config-prettier` last) and Prettier 3 (with `prettier-plugin-tailwindcss`).**
  TypeScript is a pinned `devDependency`; the ad-hoc `typescript@5.6.3` pin in the workflow
  retires with the step that carried it.
- **The generated file is excluded from both tools by path, never by in-file pragma:**
  - `web-client/eslint.config.js` opens with a global ignore object:
    `{ ignores: ['src/protocol/protocol.gen.ts'] }`.
  - `web-client/.prettierignore` contains the line `src/protocol/protocol.gen.ts`.
  - No `/* eslint-disable */` or `// prettier-ignore` header may be added to the file: its bytes
    belong to the Kotlin emitter alone, and any header not emitted by
    `generateProtocolTypes` fails the byte comparison. Ignore-by-path leaves the bytes alone.
  - The file **stays inside the tsconfig `include` set with `"strict": true`** — `tsc` reads, it
    never rewrites, and project-wide typechecking is exactly the coverage `ADR-0020` and
    `TASK-020309` promised to fold into the client's own build.
- **Dev reaches the server through Vite's proxy, and the client speaks relative URLs only.**
  Client code addresses `/api/...` and derives the socket URL from `location.host` (`ws(s)://` +
  host + `/ws`); `vite.config.ts` proxies `'/api'` to `http://localhost:8080` and `'/ws'` to
  `ws://localhost:8080` with `ws: true`. No CORS configuration on the server, no environment
  base-URL knob in the client, and production stays same-origin.
- **CI: a second job `client` in `.github/workflows/build.yml`,** parallel to `check`, with
  `working-directory: web-client`: `actions/setup-node` (`node-version-file:
  web-client/.nvmrc`, `cache: npm`, `cache-dependency-path: web-client/package-lock.json`), then
  `npm ci`, `npm run check`, `npm run build`. The script `check` is
  `tsc --noEmit && eslint --max-warnings 0 . && prettier --check . && vitest run`; `build` is
  `vite build`, so a bundle-only breakage also fails the PR. The job runs unconditionally — no
  paths filter — so the required-checks list stays simple and a skipped job can never masquerade
  as a pass. A client that does not compile fails `client`'s `tsc` step, and a red job blocks the
  PR like any other; the driver must add `client` to the required checks when the job first lands.
- **In the same PR that adds the `client` job, the `check` job drops its `setup-node` and
  `npx tsc ... protocol.gen.ts` steps** — the fold `ADR-0020` pre-authorised — leaving `check`
  purely JVM. Same PR, so the generated file is never uncovered on `develop`.
- **Nothing runs through Gradle.** No node-gradle plugin, no `:web-client` Gradle module,
  `settings.gradle.kts` untouched. The one local command for the client is `npm run check` from
  `web-client/`; `./gradlew check` continues to prove the JVM side, including
  `verifyProtocolTypes`.

## Consequences

**What it buys.** The two toolchains check in parallel, so PR wall-clock time does not grow by
the client's minutes. Everything Node lives under `web-client/` — config, lockfile, version pin —
so the JVM build cannot catch a Node disease and vice versa. The generated file is typechecked by
every CI run yet untouched by every tool that rewrites bytes. Development runs against the real
authoritative server with zero server-side accommodation. And the EOL Node 20 pin is retired at
the moment the step that needed it dissolves.

**What it costs.** `./gradlew check` no longer proves the whole repository; a contributor must
know `npm run check` exists, and the branch-protection list gains a job that a human must
remember to mark required — until then a red `client` job blocks nothing. ESLint plus Prettier is
two tools with an overlap to police (`eslint-config-prettier` carries that burden) where Biome
would be one. The ignore entries live in two small files, and a future config rewrite could drop
one; the failure is at least loud, not silent — `verifyProtocolTypes` fails the next `./gradlew
check` the moment a formatter touches the file — but the *remedy* is restoring the ignore entry,
not regenerating, and a debugger who only regenerates will loop forever. That loop is named here
so it is recognisable.

**What it forecloses.** Little, deliberately — most of this is the cheapest arrangement to
reverse, which weighed in its favour. Swapping npm for pnpm or Vite for a faster successor later
is a lockfile and a config file. The one real commitment is relative-URL/same-origin: production
must serve client and server from one origin (Ktor serving the built assets, or a reverse proxy —
a later deployment story's choice, and both stay open). A CDN split would need an env-based
base URL, which can be added then without unwinding anything. On timing: the Node 20 pin is past
EOL today, so every CI run defers a forced migration to a worse moment — a reason this decision
should not wait, not a reason it went the way it did.

## Alternatives considered

**Next.js instead of Vite.** The strongest case: the largest React corpus in training data of
any framework, and one framework decision would answer routing, building and testing at once.
Rejected because it is a server runtime: our server is Ktor and authoritative (`ADR-0002`), all
game state arrives over one WebSocket, and server-side rendering of a live table renders nothing
useful. Shipping a second server to produce static shells inverts the architecture for zero user
value; Vite delivers the same React with no runtime attached.

**Biome for lint and format.** The strongest case: one tool, one config, one ignore list —
halving the surface on which the generated-file exclusion can go wrong — and an order of
magnitude faster. Rejected on `ADR-0003`'s own criterion: it is younger and thinner in training
data, and agents will keep reaching for ESLint idioms and plugins that Biome only partially
mirrors, generating friction precisely where this project wants none. Config-only, so cheap to
revisit if Biome's corpus catches up.

**Client checks through Gradle** (node-gradle plugin, or a `:web-client` module). The strongest
case: `./gradlew check` proves the entire repository with one command, and there is no second CI
job for branch protection to forget. Rejected because it puts Node inside the Gradle build —
exactly the boundary `ADR-0020` drew and this decision keeps: a Gradle-managed Node is a second
Node pin waiting to drift from `.nvmrc`, and every JVM-only contributor's `check` starts failing
on npm weather. The one-command virtue is real but bought at the wrong seam.

**Keep Node 20 in CI, since it already works.** The strongest case: no workflow churn, and the
pin has proven itself against the generated file. Rejected: Node 20 is past end-of-life, so the
pin now resolves to an unpatched runtime; toolchains drop EOL majors first (current Vite already
holds it to a late-20 floor), and keeping it schedules a forced mid-epic migration under worse
conditions than today's free one.

**Jest instead of Vitest.** The strongest case: the largest test-runner corpus in existence.
Rejected: it needs its own transform pipeline (babel or ts-jest) configured in parallel with
Vite's, which is a second compilation truth that can disagree with what the dev server runs —
and Vitest's Jest-compatible API inherits most of that corpus anyway.

**pnpm instead of npm.** The strongest case: stricter `node_modules` and cheaper installs.
Rejected: it is not on the workstation and npm 11 is; the repository has a single Node package,
so workspace features buy nothing; and a committed lockfile with `npm ci` already gives
reproducible installs.
